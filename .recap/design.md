# Aeroflow (Flights Forecasting Services) — Design

> Generated by project-recap on 2026-03-31.

## Overview

- **What it is**: A modular Python-based data engineering and machine learning pipeline for real-time flight traffic monitoring and hourly traffic volume forecasting.
- **Problem it solves**: Captures streaming flight state vectors over specified regional airspaces (e.g., Mumbai bounding box), generates lag and rolling time-series features, outputs automated daily PDF analytics reports, and trains rolling-window forecasting models with MLflow tracking.
- **Primary users / consumers**: Air traffic analysts, ML engineers, and automated downstream alerting systems (Slack webhooks).
- **Tech summary**: Python 3.10+, Polars, PyArrow, Boto3 (AWS S3), scikit-learn, XGBoost, ReportLab, Matplotlib/Seaborn, MLflow, Docker Compose, uv package manager.

## Goals

- Ingest state vectors reliably from OpenSky Network API with configurable polling schedules and failover logging.
- Store raw data in partitioned S3 Parquet format for efficient analytical querying.
- Provide idempotent daily batch feature transformation with rolling temporal aggregations.
- Deliver automated daily PDF intelligence reports and Slack notification cards.
- Automate periodic rolling-window model retraining with full metric and artifact logging in MLflow.

## Non-goals

- Low-latency sub-second live flight tracking UI (pipeline operates on 5–10 min batch slices).
- Multi-region distributed distributed compute clusters (Spark/Flink) — pipeline uses lightweight high-performance Polars on single-node execution.

## Architecture in brief

The repository is structured as a 3-tier microservice pipeline: `ingestion` (fetches OpenSky API data every 10 min to S3), `feature-engineering` (daily batch job calculating hourly aggregations, lag features, and PDF reports), and `model-training` (3-day cycle rolling 14-day window Linear Regression forecaster tracked in MLflow). See [arch.md](arch.md) and the [diagrams](arch/).

## Key components

### 1. Ingestion Service (`ingestion/`)
- **Responsibility**: Polls OpenSky Network API, transforms raw state arrays into typed Polars DataFrames, logs runs locally in SQLite repository, and uploads partitioned parquet files to S3.
- **Location**: `ingestion/src/ingestion/`
- **Inputs / outputs**: Inputs OpenSky `/states/all` HTTP API; outputs `s3://flights-forecasting/raw/year=YYYY/month=MM/day=DD/hour=HH/states_*.parquet`.
- **Depends on**: OpenSky Network API, AWS S3, Slack incoming webhooks.
- **Used by**: Feature engineering service.

### 2. Feature Engineering Service (`feature-engineering/`)
- **Responsibility**: Ingests raw parquet files across multi-day boundaries, computes temporal and lag features (`lag_1h`, `lag_24h`, `rolling_mean_6h`), generates daily visualization reports in PDF/JSON format, and posts alerts to Slack.
- **Location**: `feature-engineering/src/`
- **Inputs / outputs**: Reads raw S3 parquet; writes hourly aggregated features to `s3://flights-forecasting/features/hourly/` and daily reports to `s3://flights-forecasting/reports/daily/`.
- **Depends on**: `ingestion` data outputs, AWS S3, Slack webhooks.
- **Used by**: Model training service and operations reporting.

### 3. Model Training Service (`model-training/`)
- **Responsibility**: Loads 14-day rolling window feature datasets, trains regression models, evaluates MAE/MAPE/R², plots forecast intervals and residual diagnostics, and registers models in MLflow.
- **Location**: `model-training/src/training/`
- **Inputs / outputs**: Reads hourly feature parquets from S3; outputs trained models, evaluation metrics, and diagnostic plots to MLflow and S3 artifact store.
- **Depends on**: MLflow server, AWS S3, `feature-engineering` data outputs.
- **Used by**: Downstream forecasting inference and model registry.

### 4. MLflow Docker Stack (`model-training/docker-compose.yml`)
- **Responsibility**: Containerized MLflow tracking server backed by SQLite metadata store and S3 remote artifact storage.
- **Location**: `model-training/`

## Data model & flow

- **Entities / schemas**:
  - `Raw Flight State`: icao24, callsign, origin_country, time_position, last_contact, longitude, latitude, baro_altitude, on_ground, velocity, true_track, vertical_rate, geo_altitude, squawk, spi, position_source.
  - `Hourly Features`: `timestamp`, `flight_count`, `hour_of_day`, `day_of_week`, `is_weekend`, `lag_1h`, `lag_24h`, `rolling_mean_6h`.
- **Storage**: AWS S3 object store partitioned hierarchically by date/time, and local SQLite for execution tracking and MLflow metadata.
- **Flow summary**: OpenSky API data is polled every 10 min into S3 raw partition; daily batch runs compile hourly counts and lag features into S3 features partition; model training service periodically queries 14-day feature windows to fit forecasting models and log artifacts to MLflow.

## Design decisions & tradeoffs

- **Polars over Pandas / Spark** — Fast columnar processing and low memory footprint for local and containerized jobs without distributed cluster overhead.
- **Microservices in Monorepo** — Independent `pyproject.toml` per service managed via `uv` allows isolated dependency management while keeping codebase consolidated.
- **S3 as Central Data Lake** — Loose coupling between microservices via S3 parquet file contracts rather than direct inter-service RPCs.
- **LinearRegression Baseline** — Interpretable, low-latency baseline for time-series forecasting with trend and cyclic features.

## Conventions

- **Language / toolchain**: Python 3.10+ managed via `uv`.
- **Configuration**: Pydantic `BaseSettings` reading from `.env` and `settings.yaml`.
- **Logging**: Loguru with structured timestamps and Slack notification handlers.
